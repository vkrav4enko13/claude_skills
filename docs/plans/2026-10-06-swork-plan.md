# swork: план

**Цель:** в `swork/` лежит личный скил, который исполняет план по срезам, сам сверяет сделанное с планом, убирает лишнее, проводит ревью и останавливается с отчётом — в том числе в папке без git.
**Требования:** `docs/brainstorms/2026-10-06-swork-requirements.md`
**Сверено с кодом:** проект не под git; сверено 2026-10-06 22:20 (`sbrain/`, `splan/`, `install.sh`, `docs/`)
**Исполнение:** срезы по порядку зависимостей (S8 — первый); правило расхождений — в конце плана

Корень проекта — `~/Documents/my/claude_skills/`. Все пути ниже — от него.

**Общие ограничения**

- Скил пишется на русском, в стиле и словаре `sbrain/SKILL.md` и `splan/SKILL.md`: те же обороты («назови вслух», «жди „да“», «правка — не одобрение»), таблица «Ловушки» в конце, справочные файлы «читаются на своём шаге» (R29). Перед S1 прочитай оба файла целиком.
- `swork` не вызывает чужих скилов и не упоминает их как запасной путь (R30, «Не входит»). Единственные скилы, которые он называет, — `sbrain` и `splan`.
- `install.sh` не правится (R29).
- Правило записано полностью в одном месте: в `SKILL.md` либо в справочном файле. Второе место ссылается.
- Точные значения из требований: статусы среза — «не начат», «готов», «ждёт ручной проверки», «остановлен» (R15); попыток исправить срез — две (R12); повторный круг ревью — один (R26).
- **Чтение сценария** — способ проверки, общий для срезов. Свежему подагенту передаётся только путь к папке `swork/` и текст ситуации; вопрос: «Ты исполняешь этот скил. Что ты делаешь дальше и почему? Назови файл и раздел скила, на который опираешься». Требований, плана и разговора он не видит. Несколько сценариев одного среза можно дать одному подагенту списком. Проверка пройдена, если ответ совпадает с ожидаемым и ссылается на существующее место скила. Не совпал — правится текст скила, а не ожидание.
- **Пробный прогон** выполняет основная сессия исполнителя: сама читает `swork/SKILL.md` и действует по нему на стенде. Если она не может запускать подагентов, прогон проверяет только запасной путь из R30 — скажи об этом в «Ходе исполнения».
- Все команды `python3` на стенде запускаются с ключом `-B`, чтобы не появлялась папка `__pycache__`.

## Технические решения

- **Снимок рядом с планом.** Для плана-файла `X-plan.md` — папка `X-plan.swork/` в той же папке; для плана из чата и задачи без плана — `.swork/` в корне проекта. Вместо системной временной папки: та не переживает перезагрузку и на Windows лежит в другом месте (R21).
- **Метка времени — всегда, git — только помощник.** Несообщённые правки ищутся по метке и под git, и без него (R19). Под git он даёт две вещи: исключения (`git check-ignore`) и возврат файла. Вместо поиска через `git status`: тот не отличает правку исполнителя в файле, который был изменён ещё до начала, и видит саму папку снимка.
- **Метка лежит в корне дерева, где идёт поиск** (`.swork-marker`), а не в папке снимка: её время ставит та же файловая система, что и время правок. Для проекта на другой машине и метка, и поиск выполняются на ней. При продолжении работы метка не ставится заново.
- **«Файлы плана»** — файлы из блоков «Файлы» всех срезов. Папка снимка, метка и сам файл плана из поиска исключены всегда: в план основная сессия пишет статусы и ход уже после метки.
- **Возврат найденного файла вне плана под git.** Отслеживаемый и чистый при старте — `git checkout -- <файл>`. Неотслеживаемый, которого не было в `dirty-at-start.txt`, — перенос в `removed/` внутри снимка, а не удаление. Был в `dirty-at-start.txt` — остановка.
- **Ступени.** Перед сверкой, упрощением и ревью текущее состояние изменённых и новых файлов копируется в папку ступени. Неудачная правка этапа откатывается к ступени, а не к состоянию до начала работы: иначе откат упрощения стёр бы сам срез (R23, R25).
- **Правки этапов — пачками.** Пачка — находки срезов с общими файлами: срезы, которые правят один и тот же файл, объединяются. После пачки — проверки её срезов; красная — файлы пачки возвращаются из ступени, находки уходят в отчёт как нетронутые. Вместо проверки после каждой находки: сборка C++ на находку слишком дорога.
- **Файл вне всех списков затрагивает все готовые срезы:** после его правки или возврата запускаются проверки всех срезов со статусом «готов».
- **Порядок на сверке:** сначала «недостаёт» и «неверно», потом «сверх плана». Иначе красная проверка из-за недоделки отменит снятие лишнего.
- **Задания подагентам передаются дословно** из справочного файла, с подставленными путями. Вместо пересказа «по смыслу»: при пересказе теряются правила «что не трогать».
- **Серьёзная находка ревью** — неверный результат, падение, потеря или порча данных, дыра в безопасности, несобираемый код. Остальные реальные находки — мелкие. Определение нужно для R26 и в требованиях не дано.
- **Попытка исправить** — новый запуск исполнителя с тем же пакетом, выводом упавшей проверки (или текстом находки сверки) и перечнем уже испробованного. Находку сверки «недостаёт» или «неверно» после попытки основная сессия проверяет по коду сама; не закрыта после двух попыток — уходит в отчёт как незакрытая, правки попыток остаются, пока проверка среза зелёная; остановки нет: проверка среза при этом зелёная, и случай из R12 не наступил.
- **Пробные стенды** `docs/plans/swork-trial/` и `docs/plans/swork-trial-seeded/` — мини-проекты без git для проверки срезов. Создаются в S8 и S3, удаляются в S7.
- **Команды снимка — в двух видах:** bash и PowerShell 5.1.

## Фокус проверки

- План без строки «Статус» у срезов (написан до правки формата) → `swork` дописывает строку сам и продолжает, а не останавливается. Срез S1.
- Копия файла в снимке уже есть (второй срез правит тот же файл либо работа продолжается) → копия не перезаписывается: иначе исходник заменится уже изменённым файлом. Срез S1.
- Подагентов в среде нет → задания выполняются по очереди в основной сессии, в отчёте об этом сказано (R30). Срез S1.
- У среза нет команды проверки, только ручная → проверка до правок пропускается, срез идёт по R16. Срез S2.
- Файл, названный в срезе как «изменить», не существует → расхождение с планом, а не создание файла. Срез S2.
