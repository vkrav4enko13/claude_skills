# Task of topic ponytail-lean

> What we build, for whom, and how we will know it worked.

## In brief

The chain writes less superfluous code from the start, is not slower and still cuts nothing needed: the most of ponytail comes into the chain through a clean room, and an edit is taken only if the stand, on the old stages and on new trap tasks, is not worse while the code is smaller.

## Task

- The executor of `swork` looks for ready-made code (rules 4 and 8) but has no ladder of cheaper options, no list of every place a change must reach and no search of callers before a bug fix; the full ladder runs only after the work, in the simplification.
- So superfluous code is first written and then cleaned up, or stays; a bug fixed in one caller can stay broken for another.
- Risky logic gets no small test: the executor may not write tests beyond the plan, and `splan` does not invent them.
- For the user (the owner of the chain), the priority is quality first, then tokens, then speed; ponytail reports less code, fewer tokens and less time at equal correctness, on its own benchmark.

## Success criteria

- The candidate series passes the acceptance of R24 against the baseline series.
- The candidate is not slower than the baseline, and the speed-up is shown as a number (R24, R26).
- Tokens and cost of both series are recorded and shown next to the quality measures (R26).
- No skill text and no stand file holds wording copied from the ponytail source (R18).
